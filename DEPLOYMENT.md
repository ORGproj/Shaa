# Deployment on Render + PostgreSQL

This project ships with a `render.yaml` Blueprint that creates the web service and a PostgreSQL database together.

## 1. Push the project to GitHub

Make sure `instance/`, `venv/` and `*.db` files are **not** committed (the included `.gitignore` already covers them).

## 2. Create the Blueprint on Render

1. In the Render dashboard choose **New > Blueprint** and connect your GitHub repository.
2. Render reads `render.yaml` and creates:
   - a web service running `gunicorn --preload --workers 2 --threads 4 --timeout 60 app:app`
   - a PostgreSQL database named `student-management-db`
3. When prompted, enter:
   - `BOOTSTRAP_ADMIN_USERNAME`: a unique admin username
   - `BOOTSTRAP_ADMIN_PASSWORD`: a strong password, 12 characters or more

`SECRET_KEY` is generated automatically, and `DATABASE_URL` is wired to the database for you.

## 3. Environment variables

| Variable | Purpose |
|---|---|
| `APP_ENV=production` | Enables production mode: no demo accounts, HSTS, secure cookies |
| `SECRET_KEY` | Session signing key (auto-generated by Render, 32+ characters) |
| `DATABASE_URL` | PostgreSQL connection string (set from the Render database) |
| `SESSION_COOKIE_SECURE=1` | Send session cookies over HTTPS only |
| `APP_TIMEZONE` | Display timezone, default `Asia/Manila` |
| `BOOTSTRAP_ADMIN_USERNAME` / `BOOTSTRAP_ADMIN_PASSWORD` | Creates the first admin on an empty database |
| `SEED_DEMO_DATA=1` | Optional. Loads sample data. Do not use with real student data |

## 4. After the first deploy

1. Open the service URL and sign in with the bootstrap admin account.
2. **Remove** `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_PASSWORD` from the service settings and redeploy. They are only needed for the first start.
3. Create the other accounts (registrar, accounting, academic) from the admin area.

## Limits to be aware of

- Uploaded photos and message attachments are stored on local disk, which is **ephemeral** on Render. Use persistent storage if you need to keep them.
- The per-IP login throttle is in memory for each worker. See [SECURITY.md](SECURITY.md) for the full production checklist.
- Concurrency tests were run on SQLite with one process, not on PostgreSQL. See [docs/TESTING.md](docs/TESTING.md).
